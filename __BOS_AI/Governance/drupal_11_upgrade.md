# Drupal 11 upgrade — environment and runbook

**Deadline is external and does not move: core security coverage for 10.6 ends 2026-12-09.**
10.6 is the final 10.x minor, so after that date a core security release will not exist for this
site. Status-of-record for the initiative is [`ROADMAP.md`](../ROADMAP.md) → NOW → "Drupal 11
upgrade"; this file is the working runbook and the record of what has been *measured* rather
than estimated.

---

## 1. The isolated environment

Created 2026-11-06. Branch `feature/drupal-11-upgrade`.

| | Primary dev | D11 upgrade env |
|---|---|---|
| Directory | `~/code/brookstone` | `~/code/brookstone-d11` |
| DDEV project | `brookstone` | `brookstone-d11` |
| URL | `https://brookstone.ddev.site` | `https://brookstone-d11.ddev.site` |
| Core | 10.6.20 | 10.6.20 → 11.4.x |
| MariaDB | 10.11 | **11.4** (matches live) |
| Branch | `main` | `feature/drupal-11-upgrade` |

### Why a separate environment and not just a branch

**`drush updb` for a major core upgrade is a one-way door on the database.** A D11-updated
database cannot be served by a D10 codebase, so a branch alone would not protect day-to-day BOS
work — checking `main` back out would leave a D10 codebase pointed at a D11 schema. The two
environments have **separate containers and separate databases**, so the upgrade can be taken as
far as it needs to go, or thrown away entirely, without touching the working dev site. Both can
run at once.

### Why MariaDB 11.4 here when dev runs 10.11

Live is on **MariaDB 11.4**; dev is on 10.11, so dev has never matched live on this axis. D11
supports both. Matching live makes this a faithful rehearsal of the production upgrade and
removes a variable from cutover day. The risk of changing two things at once is handled by
**verifying the D10 baseline first** (§2) — 11.4 is proven good *before* core moves, so anything
that breaks afterwards is Drupal 11's doing and not the database's.

### Why the project name lives in `.ddev/config.local.yaml`

`.ddev/config.yaml` is **tracked**. A `name:` or `database.version` committed there would rename
Todd's primary dev environment the moment this branch merged to `main`. `.ddev/.gitignore`
already ignores `config.local.y*ml`, so the overrides sit there instead and the branch stays
cleanly mergeable.

> ⚠ **Secret-exposure gap in any fresh clone.** `.ddev/.gitignore` is **generated by DDEV and is
> not tracked in git**, so a freshly cloned checkout has *no* ignore rule until the first
> `ddev start`. In that window `.ddev/config.local.yaml` — which holds `ANTHROPIC_API_KEY` — is
> committable. Run `ddev start` before any `git add`, or harden the root `.gitignore`.

### Recreating or discarding it

```bash
# Discard entirely — nothing else is affected.
ddev delete -Oy brookstone-d11 && rm -rf ~/code/brookstone-d11

# Recreate: clone, create the branch, copy the three untracked-by-design files
# (web/sites/default/settings.php, settings.local.php, .ddev/config.local.yaml),
# append the name + database overrides to config.local.yaml, ddev start,
# ddev composer install, ddev import-db.
```

### Known limitation of this rehearsal

The seed is a copy of the **dev** database (newest work order 2026-10-01, roughly five weeks
stale at creation). That is fine for catching *code*-level breakage, which is the bulk of the
risk. It is **not** a faithful production rehearsal, because live's active config is
intentionally drifted from both `config/sync` and dev (see CLAUDE.md → Configuration
Management), and dev's view/form displays are known to differ from live's curated ones. **Before
the real cutover, re-seed this environment from a fresh live database copy and run the upgrade
again.** A pass here is necessary but not sufficient.

## 3. Measured blockers

### 3.1 ✅ The `drupal/core` patch — flagged as a blocker, measured, and cleared

> **Written up here first as a hard blocker, on reasoning rather than measurement. It is not one.**
> Kept visible rather than quietly deleted, because the reasoning was plausible — "a patch rolled
> against 10.x cannot apply to 11.4" — and plausible-but-wrong is exactly what a runbook should
> record. **Fetch the source and run the tool; do not reason about whether a patch applies.**

`composer.json` → `extra.patches` → `drupal/core` declares a **local** patch file:

```
patches/3315678-25.patch   (strnatcasecmp — passing null to parameter 2 of type string is deprecated)
```

It touches `getSortedDefinitions()` in two places: `core/lib/Drupal/Core/Layout/LayoutPluginManager.php`
and `core/lib/Drupal/Core/Plugin/CategorizingPluginManagerTrait.php`.

**Measured 2026-11-06 against real D11 source (tag 11.4.12, the current 11.4 release — the
2026-11-02 dry run resolved 11.4.11).**

| Question | Answer |
|---|---|
| Does D11 contain the fix? | **No.** Both files at 11.4.12 still call `strnatcasecmp($a->getCategory(), $b->getCategory())` with no `?? ''`. **Keep the patch — do not drop it.** |
| Does the patch still apply? | **Yes.** `patch -p1`: file 1 at offset 17, file 2 at offset 23. (Was fuzz 1 before the hardening below; now clean.) |
| Is that worse than today? | **No.** Against pristine **10.6.20** the same run behaved identically, fuzz included. D11 adds only the offset on file 1. |
| Will upstream fix it? | **No.** Issue 3315678 (created 2022-10-17, last touched 2026-10-26, 37 comments, `11.x-dev`, plugin system) is **closed as a duplicate**, not fixed. BOS carries this patch indefinitely. |

Both signatures *did* change for PHP 8.4 — `array $definitions = NULL` → `?array $definitions = NULL`
(and `string $label_key`). That does not break the patch, because the signature appears only in
the hunk **header**, which `patch` uses as a positioning hint and not for matching; every real
context line is unchanged.

#### ⚠ Two traps found in the course of checking

**`git apply` calls this patch "corrupt at line 29" — and it never runs.** composer-patches 1.7.3
`applyPatchWithGit()` returns early unless the install path is **itself a git repo**
(`if (!is_dir($install_path . '/.git')) return FALSE;`), and composer-installed `web/core` is not
one. So **plain `patch` is the only path**, and it succeeds. The corruption is real but harmless:
the patch file is **28 lines with no trailing newline**, which is also what produces `patch`'s
"unexpectedly ends in middle of line" warning and the fuzz.

**The real risk is not a stopped upgrade — it is a silently unpatched core.** In
`Patches.php:290`:

```php
$exitOnFailure = getenv('COMPOSER_EXIT_ON_PATCH_FAILURE') || !empty($extra['composer-exit-on-patch-failure']);
```

**Neither is set**, so `$exitOnFailure` is FALSE and a patch failure **warns and continues**. A
core carrying a null-deref deprecation that nobody noticed is a worse outcome than an aborted
install.

#### ✅ Hardening APPLIED 2026-11-06

**1. Trailing newline added to `patches/3315678-25.patch`** (1724 → 1725 bytes; the diff is
nothing but the removal of `\ No newline at end of file`). **One byte did more than expected —
the fuzz is gone entirely:**

| | before | after |
|---|---|---|
| core 10.6.20 | fuzz 1 + "ends in middle of line"; `git apply` → corrupt | **clean, no fuzz**; `git apply` → accepted |
| core 11.4.12 | fuzz 1 + same warning; `git apply` → corrupt | **clean, no fuzz**; `git apply` → accepted |

So a future 11.4.x point release that shifts context can no longer tip fuzz 1 into a real
failure, and the patch now also works via `git apply` should composer-patches ever run somewhere
`web/core` *is* a git repo.

**2. `extra.composer-exit-on-patch-failure: true` set in `composer.json`.** Verified end-to-end
with `composer reinstall drupal/core` — core re-extracted, patch re-applied, exit 0, tripwire
armed.

> ⚠ **This arms a tripwire on the production deploy path.** `brookstone-sync-to-remote-DANGEROUS.sh`
> runs `composer install --no-dev` on live, so a patch failure there now **aborts the deploy**
> instead of warning and shipping an unpatched module. That is the intended trade. But note
> **3 of the 4 patches are fetched from remote URLs at install time** (`views_aggregator`,
> `page_manager`, `smart_date` — all verified HTTP 200 on 2026-11-06), so a drupal.org outage or
> a removed file is now a deploy-stopping event. **Recommended follow-up: localise those three
> into `patches/`** so patching never depends on the network. Only `drupal/core` is local today.

**3. `composer.lock` content-hash refreshed.** `extra` is part of composer's content-hash, so
changing it made `composer validate` fail and every `composer install` warn that the lock was
stale — including on live deploys. The refreshed lock changes **metadata only**: content-hash, six
`published-time` fields, and `plugin-api-version`. **No packages added, removed or changed —
316 → 316, verified by diffing the lock's package versions.**

### 3.1a ⚠ Two composer-environment findings this exposed

Both are pre-existing, neither is a D11 blocker, and both will waste someone's afternoon if not
written down.

**The two DDEV containers run different composer versions.** `brookstone` has **2.9.2**;
`brookstone-d11`, whose image was built 2026-11-06, has **2.11.1**. Whichever runs last rewrites
`composer.lock`'s `plugin-api-version`, which is why a bare `composer install` can show the lock
as modified with no dependency change at all. Harmless, but it looks alarming. The content-hash
itself is **identical across both versions** — verified by having 2.9.2 validate a lock written by
2.11.1, which it accepted.

**Composer's `block-insecure` default blocks any *constrained* resolve.** `config.audit` is **not
set** in `composer.json`, so this is composer's own default. On 2.9.2, `composer update --lock`
attempts a full re-resolve and dies on **29 problems**, every one of them "not loaded, because
they are affected by security advisories" — the fallout of the 18 advisories in §3.4. `--no-audit`
does **not** bypass it (that flag only skips the post-install report). 2.11.1 short-circuits the
lock-only path and succeeds.

**Why this is not a D11 blocker:** a lock-only refresh is forbidden from changing versions, so
every advisory-affected locked package is unresolvable by construction. A real `composer update -W`
**is** allowed to upgrade past the advisories, which is exactly what the D11 run does. Expect it to
move those packages rather than refuse. If a constrained resolve is ever genuinely needed, the
options are `config.audit.ignore` entries or `block-insecure: false` — **both are policy changes,
not fixes, and neither should be made casually.**

Either way the patch stays a **declared composer-patches entry, never a manual `sed`** — `contrib/`
and `core/` are composer-managed and re-extracted on every `composer install`, so a hand edit
silently vanishes (see `deferred_work.md`).

### 3.2 ⚠ The `better_exposed_filters` jQuery UI trap — exactly three modules, all enabled

BEF **6.0.6 requires** `jquery_ui`, `jquery_ui_datepicker`, `jquery_ui_slider` and
`jquery_ui_touch_punch`; **7.x does not**. They are transitive, not root requirements, so nothing
protects them and `composer update -W` happily removes them. **Enabled modules whose code has
vanished is a fatal, not a warning.**

Full requirer graph, measured with `composer why` (not assumed):

| Module | Enabled | Required by | Fate on BEF 6→7 |
|---|---|---|---|
| `jquery_ui` | yes | BEF **+ `jquery_ui_accordion` (root require)** | **survives** — accordion holds it |
| `jquery_ui_accordion` | yes | **root requirement** `^2.0` | **survives** |
| `jquery_ui_autocomplete` | yes | `module_filter` 5.0.5 | **survives** — module_filter holds it |
| `jquery_ui_menu` | yes | `jquery_ui_autocomplete` | **survives** via that chain |
| `jquery_ui_datepicker` | yes | **BEF only** | ⚠ **REMOVED** |
| `jquery_ui_slider` | yes | **BEF only** | ⚠ **REMOVED** |
| `jquery_ui_touch_punch` | yes | **BEF only** | ⚠ **REMOVED** |

Seven `jquery_ui_*` modules are enabled, which looks alarming, but only the three with BEF as
their *sole* requirer are at risk — the roadmap's figure is correct.

**Before upgrading BEF**, either uninstall those three (first confirming nothing still uses the
datepicker or slider widget in an exposed filter) **or** promote them to explicit root
requirements in `composer.json`.

> ### ⚠ Correction — the office warning was wrong, and why
>
> §3.2a told you to warn the office that the calendar on three billing screens would change to
> the browser's native picker. **It does not change. There is nothing to announce.**
>
> - BEF 6's `DatePickers.php` attaches **only** `better_exposed_filters/datepickers`.
> - That library declares **no jQuery UI dependency** — core/drupal, drupalSettings, jquery.

>

>
> **The lesson is about the before/after count.** 29 → 29 looked at first like the harness
> failing to detect a change. Checking *what* those 29 were — rather than trusting the number —

> evidence; it just is not self-explanatory.

#### Why two harnesses, and why status codes are not enough

**A broken geofield_map map is an empty `<div>` on a page that still returns HTTP
200.** No status-code smoke test can see it. So:

- **`web/scripts/audit_geofield_usage.php`** — asserts every plugin id referenced by
  config still *resolves*; **exits non-zero** if not, so it can gate the upgrade.
  Also catches BOS's own `hoa_boundary_map`, because it sits on a geofield field.
- **`web/scripts/test_geofield_maps_render.sh`** — logs in and asserts the map
  markup is actually in the HTML. **Dev only** — it mints a `drush uli` link for
  uid 1.

> ⚠ The Route Editor needed a different assertion from the rest: it emits **no**
> `maps.googleapis.com` script server-side, passing the key via
> `drupalSettings.bosRouteEditor.gmapKey` for its JS to load the API. So the check
> is that **`gmapKey` arrived non-empty** — which is exactly what fails if
> geofield_map ever relocates `gmap_api_key`. Getting this wrong produced a
> *baseline* failure first, which is the useful way to find out.

### 4b. A new sandbox hostname needs a Google Maps allowlist entry

**Symptom, 2026-11-06:** maps on `brookstone-d11.ddev.site` draw and then show Google's own
card — *"Oops! Something went wrong. This page didn't load Google Maps correctly."*

**This is not an upgrade regression, and the overlay itself is the proof.** For Google to
render that card, `geofield_map` 11.1.9 must have built a real `google.maps.Map`, loaded the
API and received a reply. A plugin regression from the upgrade produces an **empty div and no
overlay at all**. The key was also confirmed present in `drupalSettings` on all four map
surfaces.

**Cause.** `geofield_map.settings:gmap_api_key` is an **HTTP-referrer-restricted** key.
Confirmed directly — a web-service probe with it returns Google's own verdict:

```
status: REQUEST_DENIED
error_message: API keys with referer restrictions cannot be used with this API.
```

A sandbox hostname created today cannot be in an allowlist written before today. The fix is to
add `https://brookstone-d11.ddev.site/*` to that key's **Websites** list in Google Cloud
Console. Google warns settings take **up to 5 minutes**.

**Three traps worth knowing:**

1. **An IP restriction cannot fix this.** Google's error-messages page: *"API keys with an **IP
   addresses** restriction can only be used with web services … To use the Maps JavaScript API
   client side services, you will need to create a separate API key which can be secured with
   an **HTTP referrers** restriction."* Application restriction is a **radio button** — one type
   per key — so referrer and IP cannot be combined. The second layer that *can* be stacked is
   **API restrictions**, which is a separate section.
2. **Do not edit the IP-restricted key.** BOS has two Google keys (see `gotchas.md`): the
   referrer key for `geofield_map`, and an **IP-restricted** key for the server-side `geocoder`
   module, whose allowlist holds `65.181.121.20` (live VPS) and `68.66.226.93` (the retired
   shared box — **stale, should come off**). Flipping that key's restriction type to Websites
   would break live server-side geocoding in `bos_service_request`.
3. **Never use `https://*.ddev.site/*`.** `ddev.site` is a public domain shared by every DDEV
   user worldwide; that wildcard would authorise any stranger's local project to spend the
   project's Maps quota. Add the exact hostname.

**Also noted:** the referrer key is committed in `config/sync/geofield_map.settings.yml` and
tracked in git. That is **not** a leak — a referrer key is public by construction, shipping in
the HTML of every public BOS page — but it does mean the referrer allowlist is the only thing
between that key and someone else's billing. Keep it tight, and **remove the sandbox entry when
the sandbox is deleted.**

> ⚠ **Before tightening the referrer key's API restrictions:** `geofield_map`'s widget geocodes
> **client-side** — that is the address-search box the office uses on the property form, which
> `estimate.module` depends on. Restricting that key to "Maps JavaScript API" alone may kill the
> box while maps keep working, which is a miserable thing to debug later. Determine the APIs it
> actually calls first.
